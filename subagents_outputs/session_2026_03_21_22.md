## What We Built

Transformed a basic chatbot that grepped through files into a production-grade RAG system with per-article keyword indexing, cross-reference graphs, multi-model validation pipelines, and a Win98 brutalist frontend. Deployed to Cloud Run with GitHub Actions CI/CD.

## Session Flow

### 1. Frontend Redesign: Win98 x Brutalism

**Decision process:** Researched Win98 CSS frameworks (98.css), neobrutalism design patterns, and brutalist web aesthetics. Used AskUserQuestion to let the user choose between 4 design dimensions:
- Palette: Classic Win98 (navy/silver/black)
- Layout: Desktop window (title bar + menu bar + sidebar + status bar)
- Typography: Mixed contrast (system-ui body, Inter bold uppercase headers)
- Details: Structure only (flat borders/shadows, no pixelated decorations)

**Result:** Single-file HTML with navy title bar, `_ [] X` window controls, menu bar, chunky scrollbars, inset inputs, hard `box-shadow: 4px 4px 0 #000`, 3px black borders everywhere. Zero rounded corners.

### 2. RAG Pipeline: The Plan

Identified 3 core problems:
1. Keywords were per-chapter (82 articles sharing 10 keywords)
2. FTS5 ranking treated all columns equally
3. `search_regulation` tool scanned 275 files line-by-line

Designed a 5-phase plan through Plan Mode with user collaboration:
- Phase 1: Quick FTS5 wins
- Phase 2: Per-article .md files
- Phase 3: Database schema upgrade
- Phase 4: Keyword enrichment (multi-model agent pipeline)
- Phase 5: Verification and benchmark

### 3. Phase 1: FTS5 Quick Wins

**Changes to `app.py` and `build_index.py`:**
- Added BM25 column weights: `bm25(articles_fts, 0.0, 5.0, 1.0, 10.0)` (number=0, title=5, text=1, keywords=10)
- Normalized keywords (accent stripping, deduplication)
- Replaced file-scanning `search_regulation` tool with single `_search_db()` call
- Increased pre-loaded documents from 3 to 5

**Impact:** "reservas tecnicas" went from returning obscure CUSF 5.11.4 to returning LISF 121 (the core reserves article).

### 4. Phase 2: Per-Article Files

**New script: `split_chapters.py`**

Split 48 LISF chapter files + 225 CUSF chapter files into 2354 individual per-article markdown files in `docs/articles/`.

Unified frontmatter schema:
```yaml
ley: lisf
numero: "201"
titulo: "TITULO QUINTO - CAPITULO PRIMERO"
capitulo: "13"
tema: "DE LAS RESERVAS TECNICAS"
palabras_clave: reservas tecnicas, prima, reaseguro
resumen: ""
refs_internas: []
refs_cruzadas: []
```

**Bugs found and fixed:**
- Trailing section headers: Last article in each chapter captured next section's TITULO/CAPITULO header. Fixed with `strip_trailing_headers()`. Went from 97 affected articles to 0.
- Truncated `tema`: Multi-line YAML values in chapter frontmatter were cut off. Fixed `parse_frontmatter()` to join continuation lines.

**Per-article keywords:** Expanded regex glossary from ~30 to ~70 domain terms. Keyword diversity jumped from ~0% (per-chapter) to 89.6% (per-article).

### 5. Phase 3: Database Schema Upgrade

**Rewrote `build_index.py`:**

New schema with `context_summary` column and `cross_refs` table:
```sql
CREATE TABLE articles (id, law, number, title, chapter, filename, text, keywords, context_summary);
CREATE VIRTUAL TABLE articles_fts USING fts5(..., tokenize='unicode61 remove_diacritics 2');
CREATE TABLE cross_refs (id, from_law, from_number, to_law, to_number, ref_type);
```

Updated BM25 weights to include context_summary: `bm25(articles_fts, 0.0, 5.0, 1.0, 10.0, 8.0)`

**Updated `app.py`:**
- `_get_cross_refs_db()`: Replaced `text LIKE` full-table scan with indexed `cross_refs` join
- `_select_documents()`: Auto-includes top 3 cross-references when specific articles matched
- `correlate_lisf_cusf` tool: Uses `cross_refs` table

**Result:** 2354 articles, 1714 cross-references, 6.0MB database.

### 6. Phase 4: Multi-Model Keyword Enrichment

The most complex phase. Three-stage pipeline:

#### Stage 1: Sonnet Extraction (59 batches)

First attempted with Haiku agents (5 concurrent, 40 files/batch). All 25 batches produced junk -- Haiku used regex shortcuts instead of reading content. Resumenes were frontmatter copies, keywords included article markers.

Switched to Sonnet agents. Same batch structure but dramatically better quality. Sonnet actually read and understood each article's legal content.

**Logistics:** 59 batches of 40 files each. 5 concurrent agents, rolling launch (1 new per completion). Total: 2354 articles processed.

#### Stage 2: Generic Keyword Filter

Created `generic_keywords.txt` blacklist (43 terms: comision, institucion, informacion, disposicion, etc.). Applied as post-processing. Removed 271 generic keywords (1.2%).

#### Stage 3: Opus Validation (56 agents, 1 per Titulo)

Each Opus agent received the Sonnet-extracted metadata (not raw articles) and:
1. Capped keywords at max 15 per article
2. Removed domain-generic terms within each Titulo's context
3. Fixed empty/vague resumenes
4. Verified and corrected categorias
5. Added missing cross-references

**Concurrency:** Strict batches of 5 (user preference -- not rolling). 11 batches total + 1 final batch of 6.

**Key Opus contributions:**
- Filled ~100+ empty resumenes by reading source markdown files
- Corrected categoria misclassifications across multiple titulos
- Added discriminating compound keywords (e.g., "cesion de cartera" instead of just "cesion")
- Reduced keyword counts from up to 63 down to max 15 with intelligent ranking

#### Merge and Rebuild

`merge_keywords.py` wrote Opus-validated metadata back to all 2354 per-article `.md` files. Rebuilt database:
- 2354 articles, 2882 cross-references (up from 1714), 7.6MB
- Zero empty resumenes
- Max 15 keywords per article

### 7. Phase 5: Verification

Retrieval benchmark with 20 test queries. Key improvements:
- "modelo interno rcs": 0% -> 100% recall
- "fondos propios admisibles": 0% -> 50%
- "requerimiento de capital de solvencia": 0% -> 50%
- "reservas tecnicas": 0% -> 33%

Some queries showed lower recall because enriched CUSF dispositions (more specific) outranked broader LISF articles. This is correct behavior -- users get the most relevant content.

## Key Decisions Made During Session

1. **Haiku vs Sonnet for extraction:** Haiku cut corners on 40-file batches. Sonnet read and understood content. Quality difference was night and day.

2. **Generic keyword filter approach:** User proposed blacklist + LLM cap instead of constraining extraction prompts. This avoided false negatives and let Opus make intelligent ranking decisions.

3. **Opus per-Titulo grouping:** User's idea. Each Opus agent reviews within its domain context, so it knows "requerimiento de capital" matters more than "registro" in a solvencia Titulo.

4. **Strict 5-concurrent limit:** User enforced this after initial over-launch. Batched execution (wait for all 5, then launch next 5) instead of rolling window.

5. **API key for production, OAuth for dev:** Production uses Anthropic SDK with custom tools pipeline. Dev uses Claude Agent SDK with Read/Grep. Different code paths, unified search index.

6. **Favicon with personality:** User specifically requested a creature that honors Claude while being original. Pixel-art bureaucrat buddy with orange heart.
